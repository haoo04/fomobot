# M3 Telegram 通知与可选 AI 审核

M2 已交付实时策略候选和预风控。M3 交付规则和可选 AI 审核后的 Telegram 私聊提醒，以及可从现有候选查阅的最终风控和送达记录。理论表现和历史导出由 M4 接续。

## 实施顺序

1. 在候选和预风控写入事务中登记新实时交易候选。以不可变策略参数和收盘证据复用风控计算，结合最新盘口、市场状态和 OI 时效做最终校验。按正式信号计算冷却，保留 M2 历史查询和现货观察记录。
2. 复用管理员鉴权与密文存储，支持 Telegram 单私聊配对、解绑和发送测试。通过最终风控后原子写入正式信号与 Outbox，按照配对、时效和每日上限发送。明确失败的 429 和 5xx 最多尝试三次，遵守 `retry_after`。网络超时或发送中断记录为 `DELIVERY_UNKNOWN`，仍有效的信号可由管理员确认补发一次。
3. 接入官方 Node SDK、Responses API Structured Outputs 和 Zod。AI 默认关闭，开启后采用 `FAIL_CLOSED`，默认门槛 70 分、每日预算 USD 1、超时 10 秒。初始模型为 `gpt-6-luna` 和 `gpt-6.1-terra`。逐候选限制一次正式审核，原子预留估算成本，以实际 usage 结算，并保留清洗后的请求摘要与结果。接受和修改均经最终风控。
4. 在「通知与 AI」管理设置和测试。扩展现有候选详情与诊断，显示最终风控、AI 决策、正式信号 ID、Telegram 送达详情、队列延迟和当日 AI 用量。

## 验收

- 用空库和 M2 旧库证明迁移与历史兼容。用固定行情和模拟 Telegram / OpenAI 覆盖规则发送、AI 接受与修改、拒绝与异常、终审拦截、预算耗尽、限流、断线和重启恢复。
- 验证事务与去重、监控暂停、配对变更、过期信号和通知限额。正常负载下从收盘到进入发送流程目标为 60 秒以内。
- 运行测试、类型检查、lint、格式检查和构建。新增 SDK 由用户手动安装。真实服务联调通过管理员测试入口，使用用户配置的凭证。
- 规则通知与 AI 审核分别核对暂存差异后本地提交，并复查工作区。
